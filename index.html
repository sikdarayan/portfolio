    A QA engineer's job isn't to find bugs. It's to give the team an honest picture of what will break, what won't, and what we don't know yet — so they can make a confident decision about shipping.

    Start from risk

    Every test traces back to something that could hurt a user or the business. Coverage without priorities is busywork.

    Automate the boring, explore the unknown

    Scripts handle regression. Humans handle curiosity. I protect time for unscripted exploration — that's where interesting bugs live.

    Write for the developer

    A bug report that takes three messages to understand is one that sits unaddressed. Clarity is part of the job.

    02 — Craft

    How I decide what to test

    Testing everything equally is how teams run out of time. I start from risk — what breaks, how badly, and how likely — then allocate effort where it matters.

    PHASE 01

    Requirement Analysis

    Read specs and user stories, map acceptance criteria, flag ambiguous behaviour before a test is written.

    PHASE 02

    Risk-Based Planning

    Rank modules by impact and change frequency. P0 paths get exhaustive coverage; low-risk areas get smoke checks.

    PHASE 03

    Design & Execution

    Positive, negative, boundary, edge cases. Manual for discovery, automated for anything that repeats.

    PHASE 04

    Report & Sign-off

    Defects with evidence, coverage evidence, residual risks stated plainly, and a clear go / no-go call.

    ⏱ Timing edge case

    The dashboard that went blank at midnight

    Symptom

    Stream count showed 0 for the first minutes of every new day, then self-corrected on refresh.

    How I found it

    Manual clock advance past midnight while testing timezone handling. Nobody had tested the daily rollover.

    Fixed: aggregation now coalesces empty buckets; UI subscribes to the rollover event.

    📊 Boundary exploration

    The lookup sync that silently dropped data

    Symptom

    Configs with 501+ entries stalled at 500 and silently discarded the rest.

    How I found it

    Boundary testing at 499, 500, 501, 502. The off-by-one was invisible at 499 and only failed when I counted applied records.

    Fixed: chunked batch uploads of 100 entries with retry.

    🔀 State race

    The filter that forgot itself on tab switch

    Symptom

    Workspace filter cleared whenever the user switched tabs and came back.

    How I found it

    Exploratory session with no script. I noticed I was re-applying the same filter every time — pure habit paid off.

    Fixed: filter state moved into shared session store, rehydrated on tab mount.

      Field Notes Published September 2026 · 3 min read · Boundary testing · Time · Production

      The bug that only appears at midnight

      How a daily rollover turned into a monitoring blind spot — and why boundary testing pays for itself.

      A support ticket landed one morning. Nothing dramatic — just an observation from a night-shift operator:

      “The stream count was zero when I logged in at 12:05 AM. Refreshed, and it was fine.”

      Zero. For a night-shift operator, zero streams is the scariest number on the screen. It means either everything has stopped, or the dashboard is lying.

      I'd been testing timezone handling that week. 12:05 AM. Just past midnight. Something clicked.

      The investigation

      I opened the dashboard with an active stream, changed the system clock past midnight, and waited without refreshing. The count dropped to zero within seconds. Reloading brought it back — the actual count, unaffected.

      So the backend was fine. The UI was fine. The boundary between them was not.

      The stream count came from a rolling 24-hour bucket keyed by date. At midnight, a new bucket started empty — and the query returned that empty bucket instead of falling back to the previous day's total. The dashboard rendered 0 without checking whether the underlying data was actually zero.

      It had been in production for months. Nobody caught it because:

      • It only appeared between 00:00 and the first new stream of the day — usually under a minute.
      • Reloading (the reflex action) fixed it silently.
      • Test cycles ran during business hours.

      The fix

      1. Backend: The aggregation query now coalesces an empty bucket to the previous day's count when the new day has no data yet.
      2. Frontend: The widget subscribes to the rollover event and re-fetches immediately.
      3. Prevention: A regression test freezes time at 23:59:55, steps forward 10 seconds, and asserts the count never drops to zero mid-transition.

      The lesson

      Boundary testing is usually taught as “test 0, 1, and the maximum.” That's useful. But it misses the boundaries that matter most in production: boundaries in time, in state transitions, and in data that only exists briefly.

      Three questions I now ask before signing off any feature involving time:

      • What happens the exact moment this value crosses a boundary?
      • Who is awake when that boundary is crossed?
      • What does a reasonable user do when the value looks wrong — and does that reflex hide the bug?

      The midnight defect wasn't hard to fix. It was hard to notice. That's the job.
